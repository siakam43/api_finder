# api-fixer 函数定义判定范围设计

## 问题

实测（2026-09-22 更新前）在 `progress.json` 的 `reason` 字段中出现两类非预期的淘汰原因：

1. `"函数定义为 static，不是外部接口"`
2. `"[fallback] 原路径对应的 .h 文件中仅有函数声明和 static inline 定义，无非 static 函数体定义；scope_files 中未找到同名函数的非 static 定义"`

两类均**非必现**，重跑即消失。但它们是同一缺陷的两次显形，属"容易让模型产生错误"的点。

## 根因

1. **`static` 在 `api-fixer/SKILL.md` 中零出现。** 全文 grep 无命中，是模型自行加入的判定条件，不是提示词教的。整个流水线也不用 `static` 做淘汰依据——api-finder §五 筛选阶段判的是"有无外部输入"，与链接属性无关。

2. **两步法只列四条语法特征，static 定义四条全满足。** `api-fixer/SKILL.md:192-195` 的判定标准为：完整函数签名、签名后有 `{`、不以 `;` 结尾、不在注释中。`static inline int foo(void) { ... }` 四条全满足。模型要淘汰它，必须自己发明第五条——链接属性。上述第 2 条误报里的"无非 static 函数体定义"正是这凭空出现的第五条。

3. **放大器：§六 的"不确定时倾向淘汰"被当成通用兜底。** 该原则本用于"函数定义是否仍存在"的不确定性，但措辞宽泛。模型对"static 的函数算不算外部接口"不确定时，据此倾向淘汰。

4. **措辞根因：§三 通篇以"外部接口"为主语，却从未声明本阶段不重新判定外部性。** `SKILL.md:183` 写"将历史版本中已识别的外部接口与当前代码分析范围做交叉比对"，模型被"外部接口"这个词带向语义判定。

## 方案

**不动流程分支**，只做两处文案补充。修法定位为**声明通用原则**，不给 `static` 开特例——原则覆盖整类"模型自行追加判定条件"的问题，且不让 `static` 抢戏。

### 改动一：§三「搜索函数定义的方法」— 判定标准处补原则

判定标准位于 `SKILL.md:191-196`（"2. Read 验证"下的四条 bullet 与结论句）。该方法由 c 步（本文件存在性检查）与 d 步（fallback 搜索）共用，在此补一句可同时覆盖两个判定点。

在结论句之后、`### 流程` 之前插入：

- 旧：

```
   全部满足 → 确认存在函数体定义。任一不满足 → 不是定义，继续检查下一个候选。所有候选都不满足 → 未找到。
```

- 新：

```
   全部满足 → 确认存在函数体定义。任一不满足 → 不是定义，继续检查下一个候选。所有候选都不满足 → 未找到。

**判定只看上述四条语法特征。** 函数是否被 `static` 修饰、其链接属性为内部链接还是外部链接、
是否对外可见、是否被其他模块调用，都不参与判定——**被 `static` 修饰的函数体定义同样是函数体定义。**
本阶段只确认函数体定义是否存在，不重新判定接口是否对外暴露。
```

### 改动二：§六「抗理性化检查」— 表格追加一行

在表格末尾（`"reason 随便写一句就行"` 那一行之后）追加：

```
| "这个函数被 static 修饰，不像外部接口" | 本阶段只确认函数体定义是否存在；被 static 修饰的函数体定义同样是定义，不影响判定。 |
```

## 术语约定

- **不写"函数是 static"**，统一写"**被 `static` 修饰**"。
- 使用 C 语言规范概念作为上位表述：`static` 是存储类说明符，在文件作用域修饰函数时赋予**内部链接**（internal linkage），与 `extern` / 无说明符的**外部链接**（external linkage）相对。故原则以"**链接属性**"为上位概念，`static` 仅作其中一个例子。
- 该写法的作用是让原则讲的是"本方法只做语法形态判定"，而非"特别照顾 static"。

## 覆盖范围

- **覆盖 .h + static inline 场景。** 上文"问题"中的第 2 条误报发生在头文件场景：`.h` 中的 `static inline int foo(void) { ... }` 满足全部四条语法特征，且新原则明确"被 `static` 修饰的函数体定义同样是函数体定义"，故同样被覆盖。
- **不单独为 .h 场景加说明。** 该误报的拦截点是 static 而非 `.h`（措辞为"无非 static 函数体定义"）；单独提 .h 会让 `static` 更突出，与"不喧宾夺主"的目标相悖。

## 验证方式

本缺陷非必现，无法用重跑做可靠的复现验证。验证分两层：

1. **文案层（主）：** 核对新增文字是否无歧义地禁止了"四条之外的第五条判定标准"——即任何被 `static` 修饰的函数体定义都必须判为"找到定义"。检查改动后全文无任何可被解读为"链接属性参与判定"的表述。
2. **回归层（辅）：** 按验收标准实跑一次 `/api-fixer test_fixtures/project`，确认 10 条判定与 tag 分布与 fixture 完全一致（本次改动不应改变任何判定结果）。

## 影响范围

- **仅文案补充，不改流程。** a→b→c→d 的判定分支、进入条件、去重规则、reason 模板取值全部不变。
- **不改变任何已有条目的判定结果。** 被 `static` 修饰的函数体定义在改动前后都应判为"找到定义"；改动只是消除模型自行追加条件的空间。
- **无需同步 fixture。** `test_fixtures/project` 中只有 `static struct` 变量（`core/dispatcher.c:29`、`:38`），没有 static 修饰的函数，录制结果不受影响。
- **不考虑历史兼容。** 已存在的、含 static 误判的 `progress.json` 不做迁移。
