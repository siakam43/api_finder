# api-cleaner C 语法属性中立性设计

## 问题

**预防性改动。** api-cleaner 目前尚未观察到"因 `static` 修饰而误排"的实例，但同一致命点在 api-fixer 实测出现过（模型在提示词给定的判定标准之外自行追加"链接属性"作为判据）。

api-cleaner 的风险面**比 api-finder 更高**：

- 它的核心动作就是**排除**，不是识别——一旦把一个不该排除的接口排除掉，就是直接的数据丢失。
- 核心原则第 2 条是"更少的误报优先于更少的漏报。不确定时倾向于排除"。模型一旦把 `static` 当作"内部实现"的证据，触发的不是"降低保留倾向"，而是**直接排除**。

最可能的入侵点：

- §2.4.a 内部调用者检查的"存在任何普通函数调用 → 该函数有内部调用者，直接排除"被误扩成"`static` → 内部实现 → 排除"
- §2.2 快速排除检查里自行发明第四条排除规则

**现状：** api-cleaner **全文 `static` 零命中**（含 frontmatter）。该先验完全来自模型自身，不来自提示词——正因如此才需要显式封堵。（先前一次排查曾以为 frontmatter 里有命中，实为英文 "ext**ern**al" 匹配了 `extern` 关键词所致。）

## 方案

两处改动，全部落在 `api-cleaner/SKILL.md`，不动任何流程分支。

### 改动 1：新增「六、注意事项」，后续三个标题顺延

在 §五 约束规则 与 权限申请 之间插入：

```markdown
## 六、注意事项

以下事项适用于全部阶段，无论在哪一步做判断都成立。

1. **C 语法属性不参与接口判定。** 函数是否被 `static` 修饰、链接属性是内部链接还是外部链接，既不构成排除依据，也不构成保留依据——不因被 `static` 修饰而排除，也不因其未被 `static` 修饰而认定。判定只依据 2.4 / 2.5 的外部输入与通信边界分析。
```

同时顺延三个标题：

- `## 六、权限申请` → `## 七、权限申请`
- `## 七、抗理性化检查` → `## 八、抗理性化检查`
- `## 八、使用示例` → `## 九、使用示例`

全文没有按编号的交叉引用，顺延只改标题本身。

### 改动 2：「抗理性化检查」表追加一行

在表末（`"这个状态文件检查结果不太确定，先继续吧"` 那一行之后）追加：

```
| "这个函数被 static 修饰，应该是内部实现" | C 语法属性不参与判定，被 static 修饰不构成排除依据。 |
```

**措辞不照搬 api-finder 那一行。** api-finder 的念头是"不像外部接口"（保留侧犹疑），api-cleaner 的风险是**过度排除**，故念头写成"应该是内部实现"，现实句强调"不构成排除依据"。

## 附：`sta_reg` / `dyn_reg` 对 api-cleaner 的影响分析

**结论：零影响，cleaner 侧无需任何同步。** 三条证据：

1. **输入链路不经过该枚举。** api-cleaner 只读三个上游文件——`api-finder/api.json`（仅 `name` + `file`）、`api-finder/finder_summary.md`（中文散文理由）、`api-archreader/arch.md`。它**不读** `api-finder/tmp/feature_state.json`，而 `details.type` 只存在于该文件。
2. **摘要文件不含枚举值。** fixture 的 `finder_summary.md` 用中文散文描述注册方式（"注册为 IPC 消息处理回调"、"注册于 cmd_table[]"），不含 `static` / `dynamic` / `sta_reg` / `dyn_reg` 任一 token。
3. **cleaner 提到"注册"的位置与枚举无关。** §2.4.a 的注册点判定（约 272-281 行）用的是代码形态：`.field = func`、`{CMD, func}`、`register(func)`、`&func`，与注册模式枚举无任何耦合。

## 术语约定

- **以「链接属性（内部链接 / 外部链接）」为主词**，`static` 只作例子，与 api-finder、api-fixer 的新增表述保持一致。
- **不写"函数是 static"**，统一写"被 `static` 修饰"。
- **末句按本 skill 的实际维度收尾**（`2.4 / 2.5`），不照搬 api-finder 的"通信边界、数据来源与注册方式"——cleaner 不做注册模式分析，写进去会引入一个本阶段不用的概念。

## 覆盖范围

新增章节首句显式声明"适用于全部阶段"，因此三个可能误判的位置同时被覆盖，无需逐处添加：

- §2.2 快速排除检查（防止自行发明第四条规则）
- §2.3 判断接口形式（防止 `static` 被当作"非外部输入"的理由）
- §2.4.a 内部调用者检查（防止 `static` 被当作"内部实现"的证据）

## 验证方式

本改动是预防性的，无实测 bug 可复现，验证分两层：

1. **文案层（主）：**
   - 全文 `grep -n 'static' api-cleaner/SKILL.md` 仅命中新增的两处（注意事项第 1 条、抗理性化新行），无其他
   - 章节顺序为 ……五、约束规则 → 六、注意事项 → 七、权限申请 → 八、抗理性化检查 → 九、使用示例
   - 新章节与 §七 抗理性化检查表新行的措辞与 api-finder 的对应内容**同族但不重复**（末句与念头句按本 skill 场景调整）
   - 末尾 `2.4 / 2.5` 引用指向真实存在的小节（`### 2.4 parameter_input 深入分析`、`### 2.5 channel_read 深入分析`）
2. **回归层（辅）：** 实跑一次 `/api-cleaner test_fixtures/project`，确认 `api_clean.json` 的条目与基线一致。本改动不应改变任何判定结果。

## 影响范围

- **不影响输出格式与字段。** 仅新增约束文字与调整章节编号。
- **不改流程与判定分支。** §2.2 / §2.3 / §2.4 / §2.5 / §2.6 的规则内容全部不变。
- **不影响上游依赖。** api-cleaner 不消费 `details.type`，`sta_reg` / `dyn_reg` 换词无需同步。
- **不考虑历史兼容。** 已存在的 `api_clean.json` / `analysis_state.json` 不受影响。
