# api-finder C 语法属性中立性设计

## 问题

**预防性改动。** api-finder 目前尚未观察到"因 `static` 修饰而误排"的实例，但同一缺陷已在 api-fixer 实测出现：模型在提示词给定的判定标准之外，自行追加"链接属性"作为第五条判据，把被 `static` 修饰的函数体定义判为"未找到"。

api-finder 做的是"这个函数是不是外部接口"，比 api-fixer 更容易触发同一个先验——"外部"二字本身就暗示链接属性可能相关。因此提前封堵。

**现有的混淆源：** `api-finder/SKILL.md` 中有 3 处英文 token `static`（267、276、305 行）与 1 处 `dynamic`（286 行），全部用作注册模式的枚举值（`"type": "static|dynamic"`），指"编译期把 `{CMD, func}` 填进全局表"相对于"运行时调用 `register_func`"。这与 C 的 `static` 存储类说明符**毫无关系**，但在同一个提示词里出现同一个英文词，是潜在的混淆来源。

## 方案

三处改动，全部落在 `api-finder/SKILL.md`，不动任何流程分支。

### 改动 1：注册模式枚举换词（§三 接口特征提取）

把英文枚举值换成语义等价、且不与 C 关键字冲突的缩写。中文的"静态注册/动态注册"保持不变。

| 行 | 旧 | 新 |
|---|-----|-----|
| 267 | `    "type": "static|dynamic",` | `    "type": "sta_reg|dyn_reg",` |
| 276 | `  "type": "static",` | `  "type": "sta_reg",` |
| 286 | `  "type": "dynamic",` | `  "type": "dyn_reg",` |
| 305 | `   - 两个 pattern 同类型（都是 static 或都是 dynamic）且共享相同的注册载体（同一个 \`var_type\` + \`var_name\`，或同一个 \`register_func\`）→ 合并` | `   - 两个 pattern 同类型（都是 sta_reg 或都是 dyn_reg）且共享相同的注册载体（同一个 \`var_type\` + \`var_name\`，或同一个 \`register_func\`）→ 合并` |

286 行（动态注册的 details 示例）必须与 276 行同时改，否则两个示例不对称。

选 `sta_reg` / `dyn_reg` 的理由：不是 C 关键字，不会与存储类说明符混淆；与正文"静态注册/动态注册"一一对应，比按机制命名（如 `table|call`）更贴合现有术语。改动后 `api-finder/SKILL.md` 中不再出现英文 `static` / `dynamic`。

### 改动 2：新增「八、注意事项」，原「八、使用示例」改为「九、」

在 §七 约束规则之后、原「八、使用示例」之前插入：

```markdown
## 八、注意事项

以下事项适用于全部阶段，无论在哪一步做判断都成立。

1. **C 语法属性不参与接口判定。** 函数是否被 `static` 修饰、链接属性是内部链接还是外部链接，既不构成保留依据，也不构成排除依据——不因被 `static` 修饰而排除，也不因其未被 `static` 修饰而认定。判定只依据通信边界、数据来源与注册方式。
```

同时把紧邻的 `## 八、使用示例` 改为 `## 九、使用示例`（全文没有按编号的交叉引用，只改标题本身）。

分隔符处理：文档在各章节之间用 `---` 分隔。§七 约束规则 与 `## 八、使用示例` 之间已有一个 `---`，它保留在新章节之前；新章节与 `## 九、使用示例` 之间需补一个 `---`，即最终形态为 `---` → `## 八、注意事项` → 正文 → `---` → `## 九、使用示例`。

本节的定位是**可增长的全局约束集**——编号化以便后续继续追加条目，与「七、约束规则」并列而非并入其中：约束规则约束的是执行方式，本节约束的是判定依据的范围。

### 改动 3：「抗理性化检查」表追加一行

在表末（`"这个状态文件检查结果不太确定，先继续吧"` 那一行之后）追加：

```
| "这个函数被 static 修饰，不像外部接口" | C 语法属性不参与判定，被 static 修饰既不构成排除依据，也不构成保留依据。 |
```

## 术语约定

- **以「链接属性（内部链接 / 外部链接）」为主词**，`static` 只作例子。该表述来自 C 语言规范：`static` 在文件作用域修饰函数时赋予内部链接（internal linkage），与 `extern` / 无说明符的外部链接（external linkage）相对。
- **不写"函数是 static"**，统一写"被 `static` 修饰"。
- **中文术语"静态注册 / 动态注册"保持不变**（8 处），它们与新枚举 `sta_reg` / `dyn_reg` 一一对应。

## 覆盖范围

新增的注意事项首句显式声明"适用于全部阶段"，因此三个识别阶段的判定点同时被覆盖，无需逐处添加：

- §三 接口特征提取——种子收集与 pattern 判定
- §四 架构识别——形式一（parameter_input）与形式二（channel_read）
- §五 外部接口筛选——规则一/二/三的排除判定

改动 3 的抗理性化行针对那个具体的念头，与改动 2 的全局声明互为补充。

## 验证方式

本改动是预防性的，无实测 bug 可复现，故验证分两层：

1. **文案层（主）：**
   - `grep -n 'static\|dynamic' api-finder/SKILL.md` 无输出（改动 1 后不应再有英文 token）
   - 「八、注意事项」的首句声明了全局适用；其内容与 §五 规则二（无外部输入排除，核心规则）不冲突——规则二判的是"有无外部输入"，新节说的是"C 语法属性不参与判定"，两者维度不同
   - 「抗理性化检查」表新行与既有 6 行格式一致（2 列）
   - 中文"静态注册 / 动态注册"8 处未被改动
2. **回归层（辅）：** 删掉 fixture 的 `progress.json` 与 `tmp/` 下的状态文件后实跑一次 `/api-finder test_fixtures/project`，确认 `api.json` 仍为 7 条且与基线逐条一致。本改动不应改变任何识别结果。

## 影响范围

- **不影响 `api.json` 输出。** 换词只涉及中间状态文件 `tmp/feature_state.json` 中 pattern 的 `details.type` 取值。
- **无 fixture 依赖。** 已核实 `test_fixtures/` 下无任何文件记录 pattern 的 `type`。
- **无其他 skill 依赖。** 已核实 `api-cleaner` / `api-archreader` / `api-fixer` 均不引用该枚举。
- **不改流程与判定分支。** §三/§四/§五 的进入条件、匹配逻辑、排除规则全部不变。
- **不考虑历史兼容。** 已存在的 `feature_state.json` 中 `type: static|dynamic` 不做迁移。
