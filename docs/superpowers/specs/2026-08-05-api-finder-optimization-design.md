# api-finder 优化设计 — file 字段修正与结果校验

## 问题背景

测试中发现两个问题：

1. **file 字段存储了注册点位置而非函数定义位置：** 第五步特征识别（feature/match）中，静态注册匹配到的是注册数组/结构体定义所在文件，动态注册匹配到的是注册调用点所在文件，都不是函数定义所在文件。第六步架构识别（arch_identify）虽然在函数定义处分析，但缺少明确说明。

2. **结果中包含不在分析范围内的接口：** 新识别出的接口 file 可能不在 scope_files（如 clean_code.txt）范围内，或 file 指向的文件中不包含该函数定义。

## 设计方案

### 改动一：第五步 feature/match 子阶段 — 补充 file 字段说明

**位置：** 子阶段二"推广匹配"步骤 3

在 candidate_apis 条目格式定义后增加说明：找到候选函数后，必须追溯函数定义所在文件。`file` 字段填写函数定义所在的文件绝对路径，而非注册点/注册数组所在文件。

### 改动二：第六步 arch_identify — 补充 file 字段说明

**位置：** 分批分析循环步骤 4

在 found_apis 记录格式说明处增加：`file` 必须填写函数定义所在的文件绝对路径。

### 改动三：第七步 filter — 新增"分析范围校验"子步骤

**位置：** 逐条审查循环完成后、"输出结果"之前

对所有 `decision = "keep"` 的条目执行两层校验：

1. **函数定义验证：** grep 搜索确认 file 指向的文件中包含该函数定义。不包含则在全部 scope_files 中搜索，找到则更新 file，找不到则排除该接口。
2. **分析范围验证：** 确认 file 在 scope_files 列表中，不在则排除。

每校验一条保存一次 filter_state.json，支持断点恢复。

## 影响范围

- 仅修改 `api-finder/SKILL.md`
- 不改动数据结构、状态文件格式、progress.json 结构
- 不影响已有分析流程的阶段顺序和断点恢复机制
